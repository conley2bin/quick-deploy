# Y9000p Pi client link helper

This is the **Y9000p client half** of Pi's fullscreen Ctrl+left Markdown link opening. The company extension identifies the initiating SSH client and sends one verified target here. A failure is shown to the user, never retried against the company desktop. Y9000p web links use `xdg-open` and its default browser (which may reuse a window/tab); company file links use Y9000p VS Code Remote-SSH with `--new-window`. Ordinary left-click does not open a link. See the [short user runbook](../extensions/pi-copy-links/README.md) for `/reload`, `/copy-links`, and collision handling.

## Install and version check

**Before an idle Pi `/reload`, the installed Y9000p executable must match the company source and its v2 protocol.** From the company repository root, compare the two executable checksums and inspect the client symlink target; the target should be the intended reviewed version, not an older checkout. These read-only commands do not hard-code a machine-specific versioned installation path:

```sh
sha256sum pi-agent/client-link-helper/pi-client-link-helper
ssh -T -o BatchMode=yes -o ClearAllForwardings=yes -o StrictHostKeyChecking=yes conley-Y9000p \
  'test -L "$HOME/.local/bin/pi-client-link-helper" && test -x "$HOME/.local/bin/pi-client-link-helper" && readlink -f "$HOME/.local/bin/pi-client-link-helper" && sha256sum "$HOME/.local/bin/pi-client-link-helper"'
```

The two `sha256sum` digest fields must match. The installer `pi-agent/client-link-helper/install.sh` only creates `~/.local/bin/pi-client-link-helper` as a symlink to **its own checkout's** executable (or accepts that same existing target); it does not fetch, copy, or upgrade code and refuses another target. The Y9000p repository checkout may lag the company source, so running its old `install.sh` is **not** an upgrade. If the hashes differ, first deploy the reviewed matching executable on Y9000p and deliberately point the symlink to it, then rerun the checks; do not reload Pi against a mismatched helper. This is a version check, not an instruction to change the Y9000p host from this repository.

## Maintainer: invocation and v2 exchange

The company extension invokes a constant command (with the verified Y9000p peer/user/port pinned on SSH argv), writes one JSON request line to stdin, and **keeps stdin open**:

```sh
ssh -T -o BatchMode=yes -o ClearAllForwardings=yes -o StrictHostKeyChecking=yes \
  -o ConnectTimeout=8 conley-Y9000p '~/.local/bin/pi-client-link-helper'
```

`ClearAllForwardings=yes` on that *control request* prevents unrelated SSH-config forwards; it is distinct from the helper's two-step Y9000p→company `-L`. The command and target host are fixed; the URL or pathname is JSON stdin, never part of a shell command. Protocol version 2 is a two-phase exchange on that **same live SSH channel**. Each line is one UTF-8 JSON object; input lines and cumulative stdout are bounded at 64 KiB. Unknown/duplicate keys fail on the helper; the dispatcher validates exact response fields and target identity.

```json
{"version":2,"phase":"request","prepareDeadlineMs":45000,"action":"open-web","url":"http://127.0.0.1:8743/path?q=1#section"}
{"version":2,"phase":"request","prepareDeadlineMs":45000,"action":"open-web","url":"https://localhost:8744/path?q=1#section","backendHost":"::1"}
{"version":2,"phase":"request","prepareDeadlineMs":45000,"action":"open-file","kind":"file","path":"/home/conley/project/src/main.py","line":23,"column":4}
{"version":2,"phase":"request","prepareDeadlineMs":45000,"action":"open-file","kind":"directory","path":"/home/conley/project.v2"}
```

The helper validates the target, prepares GUI and (for company loopback) an owned tunnel, then writes `{"version":2,"phase":"prepared","nonce":"<32 lowercase hex>","ok":true,...target fields...}`. **No browser or Code is launched yet.** The company validates that target against its request, checks `OpenLifetime`, then writes `{"version":2,"phase":"commit","nonce":"<same nonce>"}` without closing stdin. A missing, early, malformed, mismatched or buffered duplicate COMMIT fails. The helper's monotonic preparation deadline is capped at 45 seconds; it polls lock acquisition without blocking indefinitely and checks channel EOF and premature bytes. Disconnect or company abort/timeout before accepted COMMIT prevents a later launch even if a queued lock becomes free. A transport disconnected after accepted COMMIT may leave the accepted desktop handoff running; company-side deadline/abort then reports failure without pretending it revoked the launch.

After handoff, the helper writes exactly one final `{"version":2,"phase":"result",...}` JSON line and exits. Errors before PREPARED yield only the final error line; errors after PREPARED yield PREPARED then the final error line. The dispatcher requires the correct line order, matching PREPARED/final target, exit status, and no trailing data. An SSH failure or absent/invalid response is an error, not permission to launch locally.

`kind` is mandatory (`file` or `directory`) and must come from the company's validated `stat`, not a laptop-side guess. `line` and `column` are positive integers for files only; `column` requires `line`. A path containing `:` with a requested location is rejected: Code's goto parser would reinterpret part of the filename as a line or report an argument error with exit 0. File paths are absolute POSIX paths **on company**. The helper never checks or opens that path on the laptop. The company opener validates source/target and file existence and sends the resource kind. Browser input is HTTP(S) without userinfo; ambiguous browser-canonicalized hosts (including Unicode/IDNA forms, numeric shorthand, trailing-dot numeric forms, and unspecified addresses) fail before desktop launch. Supported loopback source authorities are `localhost`, `127.0.0.1`, and `[::1]`. Nonstandard 127/8 and IPv4-mapped IPv6 loopback literals fail **before PREPARED**: their exact source address could remain an unowned third destination after a same-port redirect. For a `localhost` URL, the company side has already selected a reachable numeric loopback backend: `backendHost` must be exactly `127.0.0.1` or `::1`. It is required for `localhost` and forbidden for explicit-IP or external URLs; the helper does not resolve the remote destination hostname. For an explicit standard IP, that same IP selects the numeric company backend. The original URL string, including hostname, port, path, query, and fragment, stays unchanged through PREPARED, result, and `xdg-open`. The tunnel reply reports the selected numeric `remoteHost` and original `remotePort`/`localPort`.

The result's target fields are `{"ok":true,"action":"open-web","openedUrl":"...","tunnel":{...}}` or `{"ok":true,"action":"open-file","kind":"file","path":"..."}` with exit 0. Failure fields are `{"ok":false,"error":{"code":"...","message":"..."}}` with nonzero exit. `xdg-open` and `code` exit status attests that the desktop accepted a launch request; it does not attest subsequent page load or VS Code's eventual remote connection. The company integration presents errors. A live user Pi Ctrl+left gesture after `/reload` remains the final acceptance boundary.

## Maintainer: owned tunnel and desktop behavior

For a loopback web target, the helper imports the active GUI variables from `systemctl --user show-environment`, requires exactly one active local graphical session in `loginctl`, and checks X11 access (`xset q`) or the Wayland socket. An SSH shell's `DISPLAY` is not trusted. `xdg-open` uses Y9000p's default browser. For **every supported loopback source** (`localhost`, `127.0.0.1`, `[::1]`), one `-L localhost:<original-port>:<numeric-backend>:<original-port>` on a pinned private master must create **both** exact `127.0.0.1` and `::1` Y9000p listeners to the **same company backend**. This covers a same-port redirect from an explicit IP to `localhost` regardless of the browser's address-family choice. The helper checks both families against the same master PID before PREPARED and again before browser handoff. An occupied/foreign-owned family returns `port_conflict`; a missing family without a foreign listener returns `tunnel_unverified`. It never opens a single-family loopback tunnel or rewrites the URL. File and directory actions use percent-encoded `vscode-remote://ssh-remote+conley-company/...` URIs and explicit Code resource flags:

```text
code --remote ssh-remote+conley-company --new-window [--goto] --file-uri <remote-file-uri[:line[:column]]>
code --remote ssh-remote+conley-company --new-window --folder-uri <remote-directory-uri>
```

Code's positional remote-path resolver guesses file/folder from the basename, misclassifying extensionless files and dotted directories. Explicit URI flags preserve the company-side kind without reading the laptop filesystem.

The client must already configure `conley-company` as a noninteractive, host-key-known SSH alias whose `ssh -G` HostName is one unambiguous literal IP with a valid User and Port. A private mode-0700 directory under its `XDG_RUNTIME_DIR` holds a lock, per-endpoint records, and SSH control sockets. With a finite, nonblocking, channel-liveness-checked lock acquisition, the helper:

1. Captures `ssh -G conley-company` HostName/User/Port, then starts a private `ssh -M -S <socket> -fN` master with **those captured values pinned in command-line options** and the original alias retained for IdentityFile and other authentication settings. It keeps `ClearAllForwardings=yes`, `BatchMode=yes`, strict host-key checking and failure-on-forward options. Config drift after capture cannot change the master endpoint.
2. Requests only the explicit local forward with `ssh -F /dev/null -S <socket> -O forward -L localhost:<original-port>:<numeric-company-backend>:<original-port>`. The `/dev/null` config avoids the existing implicit `-R` while preserving the explicit `-L`. For an IPv6 backend, OpenSSH receives `[::1]` in the destination field.
3. Checks the master's PID via `-O check` and matches **both** exact-port `ss -H -ltnp` listeners in a single inventory. Reuse requires matching SSH identity and source endpoint/backend, plus live dual-listener PID ownership. `localhost` retains version-3 records with the chosen `backendHost`; explicit-IP records require new version-4 records including their numeric `backendHost` and source IP. Older single-family version-2 explicit-IP records, old/mismatched `localhost` records, and source/backend mismatches fail without reusing or closing an existing master. A dead control socket with a matching record can be retired and recreated. Ownership is rechecked immediately before PREPARED and browser handoff; a changed listener suppresses launch.
4. If a listener covers either client family at the original port (including wildcard/mapped bindings), the bind is unavailable, or a competing listener wins the forward race, returns actionable `port_conflict` before desktop launch. A forward reporting success with a foreign PID returns `port_conflict`; a missing family with no foreign listener returns `tunnel_unverified`. Either failure closes only the newly created private master. It does not choose an alternate port or rewrite the browser URL. Identify the conflicting listener and dependent tabs; close it only with its owner's approval, then retry the original URL.

All subprocesses use argument arrays, no target interpolation. Neither a decoy listener nor an unrelated existing `:8795` socket is touched. A newly established forward stays under the user's runtime directory for reuse until its SSH master ends or the runtime directory is cleared at logout/reboot. If the configured alias identity changes while a live record exists, the helper rejects the stale identity instead of silently reusing a tunnel to the old host.

## Validation boundary

Run `PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s pi-agent/client-link-helper/tests -v` in the repository. Fake SSH/`ss`/desktop commands test both required listeners and company-backend selection, opposite-family decoys and bind races, old-record rejection, before-COMMIT listener takeover/cancellation, unchanged URL, and preserved `localhost` and Code routing. Real local HTTP relays model both listener families: an explicit-IP `/start` returns a same-port `localhost` 302, and the opposite-family `/done` returns the company fixture body. The relays are **not** an actual SSH tunnel or Y9000p browser. The suite also exercises the installed Code resolver, bounded process cleanup, and SSH alias drift.

The corrected helper was installed on Y9000p and exercised through real company dispatcher requests with a tagged SSH client origin. A controlled opposite-family listener caused `port_conflict` before PREPARED with no browser launch; after removing that controlled listener, Chrome followed an explicit-IP page's same-port 302 to `localhost` and displayed the **company final page**, with both client loopback families served by one owned forward. A separate company IPv6-only `localhost` page displayed correctly through the same dual-family client design. Code Remote-SSH file opening was physically checked in an earlier v2 run. Those controlled fixtures/masters were removed; at this documentation checkpoint the active user Pi has **not** yet been `/reload`ed or activated by a physical Ctrl+left gesture. That live click remains the acceptance boundary.

An existing manual Y9000p `:8795` forward is still separate; the helper returns `port_conflict` instead of adopting or closing it. Identify its owner and dependent tabs before explicitly retiring it with owner approval. Both-family ownership covers the initial port and same-port `localhost` redirects; redirects to other ports/authorities are outside this guarantee, and a company service can stop after the tunnel is prepared.
