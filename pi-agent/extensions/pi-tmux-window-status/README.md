# Pi → tmux breathing status

This extension exposes **logical Pi work** and latched root assistant/model errors, not terminal-process activity, in the tmux window status line. It owns presentation only; [pi-suspend-guard](../pi-suspend-guard/README.md) owns all automatic `continue` sends, including outside tmux. Lifecycle behavior is checked against Pi 1.4.0.

- `agent_start` marks the local root Pi turn active; only `agent_settled` returns it idle.
- Only the root Pi process publishes leases. Nested child Pi processes (`PI_SUBAGENT_DEPTH > 0`) are ignored so a child paused for attention cannot keep the parent window active.
- pi-subagents 0.56 `subagent:async-started` / `subagent:async-complete` events add and remove detached child work only when their `sessionId` matches the root Pi session. If a terminal top-level async root has a trusted `nestedRoute`, the extension retains it until the read-only nested registry sidecar shows all descendants terminal. If completion includes live nested children but no trusted sidecar, the extension logs that the root is retained failure-closed until session shutdown because no authoritative source can prove terminal.
- `subagent:control-event` with `needs_attention` makes that child/node idle immediately. Its atomically written `status.json` and, for terminal roots, `dirname(nestedRoute.eventSink)/registry.json` are watched; newer projected activity reactivates it. Missing, malformed, or mismatched nested registries are failure-closed active and retried by the heartbeat. A waiting child therefore cannot hide a concurrently running sibling.
- A private atomic lease is written while work is active (`state:"active"`) or an assistant error is latched (`state:"error"`). It expires after 6 seconds, repairing crash leftovers. Leases never store raw error text.
- A 2-second repair monitor stays alive while the root turn or any tracked child exists. It refreshes retained terminal-root registries and publishes an active lease only when logical work is active; attention-idle children keep repair running but do not start breathing. The lease diagnostics contain the parent Pi session ID plus sorted active top-level run IDs and active node IDs. They deliberately exclude prompts, history, cwd, and names.
- Every root message with `role:"assistant"` and `stopReason:"error"` latches ERROR, regardless of `errorMessage` wording or whether it exists. Concurrent `permission_error`, session-source, unknown/empty, auth/quota, schema and context errors all qualify for suspend guard recovery. Tool/toolResult failures and ordinary assistant text containing `Error:` do not independently trigger it.
- The sole sender, suspend guard, waits **60 s since the latest terminal assistant error**, then sends only after native `agent_settled`, idle and no queued input. It sends at least 60 s apart, at most **5 times per error trigger**. Each new terminal assistant error, including after an automatic continue, resets the deadline and five-attempt budget; consecutive errors can therefore produce more than five sends overall. Duplicate delivery and message updates do not renew the trigger. Normal completion/model selection end the old trigger, and Esc cancels it. This extension has no send timer or legacy fallback. A trigger with no new terminal error may exhaust its five attempts while the window stays red; a genuinely new error renews the budget. See the recovery owner's README for input priority and bounded watchdog behavior.
- The red latch survives retry/agent start/settlement and clears on semantic assistant output, normal assistant completion or model selection. Sending `continue` never clears it. Thus red indicates a latched assistant failure, not a diagnosis of provider availability.
- An ordinary abort may retain the red latch; manual Esc clears it as described below. Suspend guard handles aborted assistant messages and explicitly aborted settlement. Pi 1.4.0 retry-sleep Esc may settle `aborted:false`, and idle Esc emits no lifecycle event, so raw terminal cancellation is essential. Legacy `Aborted after N retry attempts` tails preserve only an existing recovery candidate and never override explicit cancellation.
- Manual cancellation is pane-owned. Error leases include their pane IDs, and the animator derives pane option `@quick_deploy_pi_recovery_armed` from the currently live error leases while deriving aggregate window `@quick_deploy_pi_error`. It sets current owner markers and clears previous, expired, reused, and startup-stale markers in the same tmux command batch as the window state. The tmux root and copy-mode Esc bindings require both options, then prepend a private CSI sentinel before the real Esc. Either extension can consume the sentinel; both observe the shared `pi-suspend-guard:cancel` event with `{ signal }`, so listener order cannot hide cancellation from the sender or status publisher. The real Esc retains Pi/search behavior, and raw Esc observation also works outside tmux. Cancellation records the active run signal, clears this root's recovery candidate/red lease and ignores same-run delayed errors. A distinct run may recover normally. Esc does not reset the 60 s send interval or renew the cancelled trigger's budget.
- Tmux copy-mode search prompts consume input before root or copy-mode tables. Vi `/` and `?` retain their native submit-on-close searches. Native emacs `C-s`/`C-r` use `command-prompt -i`, which releases the command queue immediately and cannot provide a close callback; these two bindings are deliberately changed to native submit-on-close searches while preserving direction, initial `#{pane_search_string}`, labels, Enter/Escape behavior, and unarmed zero-byte routing. All four append an armed-only sentinel after closure. Tmux 3.4 exposes no cancel-only result and cannot distinguish Escape dismissal from Enter acceptance at that continuation, so either closing path cancels recovery while armed.
- One detached animator per tmux socket uses a PID/token-owned exclusive lock and remains the sole writer of window presentation and pane recovery-marker options. ACTIVE updates at 24 frames × 42 ms/frame (~24 FPS), a ~1.0 s monotonic-time cycle; ERROR is steady `#d70000` with `#ffffff` text and otherwise reconciles at a slow 1 s cadence. Before submitting a semicolon batch, the animator retains cleanup responsibility for the union of prior and every attempted window/pane target; only total command success narrows that set to the current aggregate. Thus a trailing client-refresh failure cannot strand options already applied earlier in the batch. Lease owners request urgent recomputation by signaling the lock PID with safe `SIGWINCH`; signal callbacks serialize after an in-progress frame, then repaint from fresh aggregate leases. The listener is removed on animator stop. Delayed callbacks skip to the correct phase instead of stretching the animation.
- Both selected and unselected windows breathe the same gray palette `#bcbcbc → #f5f5f5 → #bcbcbc → #808080 → #bcbcbc`. Selection is no longer a blue background block; instead the selected tab draws two-cell full-block `#0077aa` bars at each end (`██`, with both fg and bg blue so even font-rendered gaps never show the block color) — a visual channel orthogonal to the background, so a selected window with a latched error shows the red block plus solid blue ends instead of losing the selection cue. The bars never breathe and never change color. Oh My Tmux's generated pre-`#!important` reload stage is configured with the same blue-rail/gray-center semantics, so a config reload cannot transiently fall back to its default whole-blue selected tab.
- The animator caches attached tmux clients for roughly one second. Each rendered frame is one semicolon-batched tmux update containing all active/reset window-option commands and all cached-client `refresh-client -S` commands. Zero or temporarily stale clients do not stop the helper permanently.
- On startup the animator clears stale window options with no live lease; it exits—and clears its active/error window options—when no live lease remains. Window priority is ERROR > ACTIVE > IDLE.

## Deployment

Install the status publisher and its separate recovery owner from the same checkout (`pi-agent/install.sh` and `fresh-install/modules/tmux/install.sh` install both):

```bash
bash pi-agent/extensions/pi-suspend-guard/install.sh
bash pi-agent/extensions/pi-tmux-window-status/install.sh
```

The status installer alone enables presentation, not automatic recovery. Its shared input/error helpers come from the sibling suspend-guard source directory; keep the checkout intact. Disabling the suspend-guard extension leaves status reporting enabled but no automatic sender.

It creates exactly one managed link:

```text
~/.pi/agent/extensions/pi-tmux-window-status
  → <checkout>/pi-agent/extensions/pi-tmux-window-status
```

An exact link is skipped. A stale symlink at the new path whose target suffix is recognizably `pi-agent/extensions/pi-tmux-window-status` (for example after a checkout move) is backed up and replaced. The legacy name `~/.pi/agent/extensions/quick-deploy-tmux-status` is still recognized: when it is a known managed link to this repo's old extension path, it is treated as a legacy install and migrated — backed up with a timestamp and then replaced by the new link. Unknown files, directories, and foreign symlinks at either path are left untouched and cause a failure; if both old and new paths exist, the installer proceeds only when both are known managed links and otherwise fails without mutating anything. The installer accepts `PI_TMUX_WINDOW_STATUS_SOURCE`, `PI_CODING_AGENT_DIR`, `PI_TMUX_WINDOW_STATUS_TARGET`, and `PI_TMUX_WINDOW_STATUS_LEGACY_TARGET` for isolated tests.

**Runtime contract is intentionally unchanged by this rename.** tmux window options remain `@quick_deploy_pi_*` and the private lease directory remains `quick-deploy/pi-tmux-status`; only the managed symlink name changed. This keeps already-running Pi processes and outstanding leases working and creates no duplicate runtime state.

On startup/reload, restoration reads only pi-subagents 0.56's active-run index under `ASYNC_DIR/.active-runs` beneath `PI_SUBAGENTS_TEMP_ROOT` (or its default scoped temp root), and adopts only status files whose `sessionId` matches the current Pi session. It does not scrape arbitrary directories.

## Pi auto-discovery

Pi does **not** scan this repository. At startup Pi loads extension directories it finds under `~/.pi/agent/extensions/`, which is exactly what the managed symlink above provides; the tracked extension under `pi-agent/extensions/pi-tmux-window-status/` is inert until that link exists. After installing or updating the extension, **restart Pi or run `/reload`** so the new code is loaded. Reloading tmux changes the status format and sentinel key routing only; it does not load the Pi extension. The current Pi process is not reloaded by the installer.

The status format deliberately uses absolute styles so activity color always wins. `last` and `activity` overlays therefore retain their label semantics but do not change background; bell preserves yellow foreground and `!`, and zoom preserves `Z`, while the active/idle background remains authoritative. The dark edge cell still separates adjacent tabs. Integration tests scrub `TMUX` and every `TMUX_*` variable before starting explicit-socket servers; otherwise Oh My Tmux's asynchronous secondary clients can follow an inherited outer socket and mutate the user's live status format.

Runtime state is private under `${XDG_RUNTIME_DIR}/quick-deploy/pi-tmux-status` (or `${XDG_STATE_HOME:-~/.local/state}/quick-deploy-runtime/quick-deploy/pi-tmux-status`) and must never be committed.

## Diagnostics

When Pi is outside tmux, tmux identity resolution fails, or an async payload is malformed, the extension writes an explicit diagnostic to Pi's stderr and does not fabricate activity. This needs the `pi-subagents` extension in the same root Pi process to receive its async event bus channels.
