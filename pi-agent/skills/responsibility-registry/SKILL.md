# Global Responsibility Registry

## When to Register

- Register only genuine, explicitly authorized **ongoing responsibilities**. The user may appoint owners; an immediate superior may also appoint subordinates and assign goals within their own authorized scope. Record the issuer and authority evidence; do not treat arbitrary peer suggestions as authorization. First distinguish appointments from ordinary execution requests, discussions/examples, and negations; "Suppose I said you were responsible for..." and "I do not want you responsible for..." create no appointment. Do not invent appointments.
- A helper implementing a short-term subtask is not an ongoing owner; inherited context or cwd does not automatically warrant registration. Add an owner only with a separate explicit ongoing appointment; do not mistake your work implementing this skill for a user appointment.
- The source belongs in quick-deploy's `pi-agent/skills/responsibility-registry/`; from the repository, run `bash pi-agent/install.sh --skills-only` and select only this skill in the menu; the installer copies it to `~/.pi/agent/skills/responsibility-registry/`. That global directory is the installation target, not a development location. Pi discovers the installed `SKILL.md` globally; existing sessions must run `/reload`. The model loads this skill by intent; it is not a startup hook and cannot guarantee a match for every natural-language request. The user can force loading with `/skill:responsibility-registry I appoint you as the owner of...`. Sessions with skills disabled must enable them first.

## Taking Responsibility and Registering

1. Turn the appointment into a bounded project/task scope, goals, and acceptance criteria. Record the `goal_source` issuer (`user` / `owner:<ID>`) and genuine source evidence. Immediate superiors decompose goals downward; refine implementation steps only within authorization, without expanding the goal. Ask your immediate superior about goal/authority questions first; the superior escalates through successive levels if needed.
2. **Reread the current live Markdown / CLI query before every action**. After a reset, do not reappoint yourself from old task memory, history, old JSON, or an old consultation plan; omitted owners/responsibilities no longer have current registry authorization. Read the same registry first: check the relevant projects/tasks, existing owners, superiors, and dependencies. An owner ID identifies an ongoing responsibility holder, not a session name; generate it initially with `python3 -c 'import uuid; print(uuid.uuid4())'` and save the current `era` with the owner ID. When recovering context, first compare the era and check the current row; registry authorization exists only while that row remains in the current live Markdown. If the era has changed and the row is absent, an old appointment message/memory cannot justify re-registration; a new appointment is required. Without evidence, do not infer identity from a role name/cwd. One owner may hold multiple scopes, each with a stable responsibility ID and a project-local task ID.
3. Verify **your own** identity: call `intercom` `status`, then `list` to check `Current session`; do not select the first session sharing the cwd. An Intercom ID is a contact address and may differ from the actual Pi session ID. Obtain the actual Pi ID only from verified current-session metadata (Pi `/session`, the host's current-session information, or the header of a session file explicitly matched to the current session). Do not infer it from the newest file, another session, or a subprocess environment; do not start a new Pi/CLI bridge to obtain an ID. If the contact ID is verified but the Pi ID is unavailable, set the latter to null with source `intercom-status`; if neither is available, set both to null/source `unavailable`, state why, and registration may still proceed. See [CLI](references/cli.md) for the exact format. Also save in the owner's `recovery` the verified absolute session-file path, original cwd/repo/worktree, handover summary/key decisions/open questions, and document pointers; use null and a missing-data reason for unavailable items, never construct a path from an ID. Update session/context changes with update-owner. Handover copies the predecessor's actual Pi ID, contact ID, recovery, and goals into a historical snapshot; do not overwrite it with their later new session. The tools check field consistency only; the caller must establish authenticity from the evidence above.
4. Establish the immediate superior: register as a top-level owner with `parent: user` only when the user explicitly appoints you directly and there is no existing or specified reporting recipient. An initial user appointment does not dissolve an already explicit subordinate reporting chain; if appointed by a superior, parent is that authorized superior. Preserve an unregistered superior as `owner:<stableID>` and clarify the relationship with the appointing party/known immediate superior; do not unilaterally change it to user or treat yourself as a top-level owner. In that state, do not claim you can report directly to the user. Derive subordinates from parent; dependencies and peer collaboration do not change the reporting chain.
5. Obtain the current `document_token` through query. After checking the genuine appointment and current parent, every write command (including register) must carry `--expected-document`; commands with expected-revision still require the revision. Register through the CLI and read the current live Markdown. **One project may have multiple owners for different tasks/directions**; reject a new claim only when the same task already has a lead, and do not evade this by changing the task's spelling. Check semantic overlap before expanding/splitting scope; changing another owner's scope, transferring responsibility, or changing a superior requires authorization. `--actor user` records existing authorization; it is not a power switch. Tasks also record canonical repo identity (Git common dir) so owners in the same repository can be found across projects/worktrees.
   Examples only, not appointments or registrations: one project may have both an office-scenario evaluation owner and a kitchen-scenario evaluation owner. Likewise, the same Dexathlon_task-proposals repository may have an owner for web publishing management, an owner for publishing office-scenario data-collection tasks, and an owner for publishing kitchen-scenario data-collection tasks, each with clear goals and a superior.
6. Only top-level owners report to the user; middle/lower-level owners report the responsibility ID, goals/acceptance criteria, superiors/subordinates, contact status, registry path, and next action to their immediate superior. Superiors aggregate upward through each level; do not bypass an existing chain because the user made the initial appointment. Completed registration does not mean the goal is complete.

**Sole source of current truth**: `~/.pi/agent/skills/responsibility-registry/RESPONSIBILITIES.md`; `RESPONSIBILITIES.template.md` in the same directory is a completely blank template. Names/roles/Parent in the visible tables are editable; queries, authorization, and the web view follow the current rows. Details contains only the remaining, nonduplicated fields; History is audit-only and does not restore current rows. Use the CLI when ownership changes need attribution. The old `dashboard.md` retains only a pointer tombstone with no relationships; on-demand reports go to stdout/an explicit path and cannot serve as current authorization. Private locks/migration backups live in `~/.pi/agent/.memory/local/responsibility-registry/`; do not upload them to a remote or commit runtime state.

## User Cancellation, Rebuilding, and Restoration of Relationships

- When the user directly says "Cancel all owner relationships" or "Rebuild owner relationships": first query the current live Markdown and verify genuine user authorization, then call `clear --actor user --expected-document TOKEN --reason ... --authority ...`. **The registry may remain empty without any subsequent appointment**. A role-bound peer/superior identity alone grants no authority to clear the global registry.
- If the same user message also says "I appoint you as...": complete clear with its backup first, then query the new era and **register only that explicit new appointment**; infer no other responsibilities from old memory. The template may still be copied manually; agent clear automatically uses a new empty UUID era, with no user-supplied ID required.
- Every agent clear/restore first saves the current live Markdown's **raw bytes**, under the same lock, to private `backups/` in the same directory, named with timezone-aware second-resolution time, a sequence number, and a UUID (directory 0700/snapshot 0600). `BACKUPS.md` (0600) lists time, user authority evidence, root names and parent→child/roles, counts, path/ID, hash, and status. This index and the snapshots are historical evidence, not sources of current authorization.
- For "Restore the previous relationships/those at a specified time": `backup-list` lists completed candidates; first parse the target and verify its hash/format. If ambiguous, list candidates and ask the user; do not guess. previous means **the latest completed pre-switch snapshot at the start of this request**; select the target before backing up the current state, so repeated previous can toggle between the last two states. Time-based restoration requires an explicit timezone (e.g. `2026-10-24T16:13+08:00` or `2026-10-24T08:13:05Z`) and matches the instant interval for that minute/second. With no timezone or multiple candidates, list UTC/local times with offsets and ask the user; do not assume UTC. `restore --target ...` backs up CURRENT first, then restores the target relationships/history as-is with a new UUID era; old tokens/plans are not restored. Only this skill's registered `backups/*.md` are allowed, never legacy JSON/dashboard. Restoration does not restart agents/jobs or restore execution state. If agreement confirmations in an old snapshot lack terms evidence, those agreements remain explicitly not-ready; do not supply confirmations automatically.
- A backup/index write failure forbids switching. An index failure after switching returns nonzero with `switched; index incomplete`: first query to verify the current graph, then use user-authorized `recover-switch` to reconcile each hash. pending/incomplete entries do not qualify as previous and block further write commands. A failed switch known not to have been published is marked aborted and its journal cleared on a best-effort basis. If, in the meantime, user edits or manual rm+cp produce another **valid** current live Markdown, recover records only the terminal state `superseded-manual` (observed hash/original phase), retains the snapshot, completes the index, and clears pending without writing the live file. That record does not automatically qualify as previous; if its sequence number is newer than the latest completed entry, previous refuses, lists both UTC/local times, and asks the user. If the user explicitly selects its full ID/filename, that snapshot may be restored after hash/v2 validation, still backing up CURRENT first. Preserve explicit recovery evidence if the index fails. Never treat nonzero as proof that no switch occurred and blindly repeat the operation.
- If the live file is missing/corrupt, report the precise diagnosis first and let the user decide on repair/manual replacement; **never cp the template yourself to "fix" it**. Before the user decides on replacement, save any existing corrupt raw bytes as a private 0600 dated copy; if the file is already missing, explicitly state that no existing bytes can be backed up. A raw corrupt backup is evidence and must not be presented as a parseable restore candidate.
- **Manual OS rm cannot be intercepted**: it deletes that era's history in this file (including new post-migration events) and does not automatically back up unobserved manual edits. Prefer agent clear for complete retention; make your own private dated copy before manual deletion. Copying the same-directory template after manual deletion still immediately means a zero current graph. Missing/corrupt files never trigger imports of old JSON/caches; no JSON deletion or service restart is required.
- To serialize a manual reset with the CLI, use the same-`flock` rm+cp example in [CLI](references/cli.md). A noncooperating editor still has a race between the final recheck and rename; do not claim absolute overwrite prevention. Reset changes registry authorization only; it does not stop running agents/children, and every owner must reread the current live Markdown.

Reinstallation preserves the current live Markdown/index/snapshots and does not recreate missing files after prior initialization. Old JSON is usable only through an explicitly authorized one-time migration; the old dashboard is archived and replaced with a pointer tombstone containing no relationships. `rebuild` only emits a report marked non-authoritative to stdout/an explicit path; **the natural-language request "Rebuild owner relationships" uses clear above, not the report command**. See [CLI](references/cli.md) for exact reset/restore/recovery commands and [migration](references/migration.md) for migration and fallback without resurrecting old data. This runs locally on Linux/macOS with POSIX+the Python standard library; it is not a cross-host service.

## Owner Operating Contract (Throughout the Appointment)

- **Every owner must actively advance the overall goal**; their primary responsibility is the overall goal, prioritization, orchestration, and acceptance. Once the user/superior has set the goal, acceptance criteria, and constraints, by default adopt the owner's recommended approach to routine internal details that neither materially affect the overall goal/direction nor involve major commitments, and delegate execution immediately. Do not stop with "Should I continue?", "Would you like me to do it?", or "Waiting for confirmation of implementation details". Discuss major decisions or questions that may affect the overall goal/direction with the user first through the chain below, even if apparently in scope. Explicit requests for discussion/hypotheticals remain discussion only; they create no appointment and do not start implementation. Maintain a priority queue and dependency graph **visible to the immediate superior (the user for top-level owners)**, using task documents if sufficient: task IDs, inputs, scope, priority, prerequisites, subtask run IDs, deliverables, acceptance criteria, status/blockers, and next actions. The registry stores stable responsibilities and relationships, not every log entry. Synchronize dependency changes to registry `depends_on`.
- **Distribute goals level by level through the currently registered team**: after the top-level owner agrees on overall goals/plans with the user, first query existing owners, parents, and responsibility scopes; assign bounded goals, scope, acceptance criteria, and dependencies item by item to existing immediate subordinates. Each level decomposes further to its own immediate subordinates; each owner's own authorized async subagents still implement the concrete work. Do not construct a replacement staffing structure, replace/bypass existing direction owners, or assign across levels. Missing direction owners, overlapping responsibilities, or assignment conflicts are explicit gaps to resolve through the reporting chain, not reasons to invent appointments. Escalate major decisions level by level to the top-level owner for discussion with the user; propagate settled decisions downward through each level. Advance routine details within authorization and report progress/results to the immediate superior.
- **Delegate concrete implementation, debugging, business-file edits, test execution, deployment/operations, and integration commands to your own authorized async subagents**. Owners may reason, read artifacts, coordinate decisions, operate this registry, maintain task notes, review deliverables, and make acceptance judgments; implementation subagents also make code changes needed for integration. There are no "small/simple/faster/hotfix" exceptions; do not implement work yourself under the label of "integration". Missing authorization/tools/available executors is a delegation blocker: ask the immediate superior to restore the required capability, never implement it yourself as a fallback.
- Check the actual tools first. If `subagents_enable` is available and delegation is allowed, enable it, then use `subagent` `list` (`capabilities: true`) and `get`/`guide` to read current capabilities and governance. Use existing profiles and current model-routing rules; do not invent providers/agents/APIs. **Delegate only asynchronously** (explicit `async: true`); do not pass off a foreground CLI/another session as your own child, or require an unauthorized child to fan out recursively. This skill cannot override tool limits or parent prohibitions.
- Each named child task must include input evidence/locations, allowed change scope and invariants, deliverable path, acceptance criteria, **reporting to this immediate owner**, and blocker-escalation rules. Keep ongoing responsibility owners separate from these temporary workers; do not add every worker to the global owner table. If an ongoing subordinate really needs appointment, obtain explicit authorization first and register their genuine identity and parent, not a run ID as an owner.
- **Before dispatching a mutation worker**, query existing direction owners by canonical repo ID and negotiate laterally on file/module write boundaries, shared files/interfaces, branch/worktree choices, order, integration owner, and acceptance. Record affected directions and terms in the same registry with `coord-propose`; after each participant has genuinely and explicitly agreed, each submits `coord-ack`. Sending a message/receiving a delivery receipt is not agreement; never fabricate a peer's ack. The current query's `agreement_ready` means only that the listed agreements have been confirmed, not repository-wide authorization or a writer lock.
- Only one active writer per cwd. Isolated worktrees can run in parallel, but still require explicit agreement on handling overlapping files/interfaces and on integration order. Release the old agreement and renegotiate when boundaries/goals/acceptance criteria change. Unknown/unreachable peers or unconfirmed overlaps block only the related overlapping mutation; continue planning, read-only work, and demonstrably nonconflicting work (e.g. independent tasks within already explicit valid boundaries). Do not halt the entire project or mark unconfirmed work ready.
- Do not overwrite others' work or independently stage/commit another owner's changes; the agreed owner organizes integration through their own implementation child. Ordinary delegation grants no permission for cross-scope changes, external writes, publishing, or messaging. Peer coordination is lateral collaboration and does not automatically change parent.
- Route routine helper questions to their owning responsible agent. Owners must actively identify major decisions or questions that may materially affect the overall goal/direction (e.g. success definition, key strategic approach, major scope/priority tradeoffs, or resource commitments), analyze impacts/options/recommendations, and state the precise decision needed. **Being in scope or approved by an intermediate superior is not final user approval**: middle/lower levels report to their immediate superior, each level escalates to the top-level owner for discussion with the user, and the user's decision propagates downward through each level with goal/plan updates. Do not commit to or implement the disputed direction beforehand. You may delegate bounded, noncommittal evidence collection, but not use "exploratory experiments" to implement it first or imply a major commitment. The criterion is material impact on goals/direction or a major commitment; uncertainty alone or an ordinary tool/library choice does not make a major decision. Report other authority or shared-repository boundary issues to the immediate superior as well. Pause only the affected branch while a decision is pending; independent work continues. Middle/lower-level owners must not bypass the hierarchy to report progress or seek decisions directly from the user.
- **Whenever a child result, failure, or new evidence arrives, assess acceptance/revise judgments against the remaining gap to the overall goal, reprioritize tasks and dependencies, and immediately dispatch the next ready task**. Do not wait for the entire batch or stop after one step to discuss routine details. A finished subtask, commit, test, or report does not mean the overall goal is complete; keep independent paths moving when one is blocked. For native subagents, use async completion notifications only; **never block waiting for a child or call bg_wait for same-turn results**. When all work that can advance is already in active children and no other work is ready, yielding the turn fulfills the responsibility; native notifications resume progress, with no need to ask whether to keep waiting. Otherwise, when no work is ready, state the blocker and next trigger before yielding. Do not sleep/loop over status; necessary diagnostics must target an explicit run ID. Handle independent provider jobs without native notifications according to their tool contracts. Stop the corresponding work when the appropriate superior accepts the overall goal, or upon receiving an explicit pause/handover instruction; do not manufacture work indefinitely.
- **Retain all established project owners, old appointments, and responsibility start/end times long-term within the current era**. Session termination/offline status does not delete an owner or automatically end/transfer responsibility. After any owner/responsibility/superior/goal change, the relevant owner or authorized immediate superior proactively updates the shared registry without waiting for a user reminder. History appends semantic events showing, in the same Markdown, who handed over to whom, IDs/names/roles, scope, timezone-aware second-resolution time, and authority evidence; look up current owners separately through `query --active` / `current_owners`.
- Goals, goal changes, and acceptance decisions propagate downward from superiors; progress, blockers, and deliverables aggregate upward through each level. Intermediate owners accept child work within authorization, receive their immediate superior's decisions, and pass them down; do not change superior goals unilaterally or send all acceptance decisions to the user. Delegate specific corrections after failed acceptance. Use `close` after the appropriate superior accepts the goal; use `handover` to retain history during transfer, and do not manufacture tasks indefinitely. A child's self-reported success is not acceptance.

## Lookup, Contact, and Handover

- **Locate by responsibility first**: before any task-related question, verification of a hunch, collaboration, progress/result message, or skill-update notification, read the current `RESPONSIBILITIES.md` or a read-only CLI query. Match the most directly responsible owner by concrete project/task, canonical repo, responsibility scope, and shared interfaces/dependencies; verify owner ID, superiors/subordinates, lifecycle, and contact ID.
- **Minimum recipients**: normally contact one directly responsible owner. Use the smallest affected owner set only for a concrete shared boundary/dependency, explaining each recipient's relevant responsibility. A shared project/repository/cwd or an online list is not a recipient list. Technical peer consultation stays lateral; decisions/progress still follow the existing reporting chain. Child questions should first use the actual supervisor-contact tool to reach their immediate owner.
- **Select the person before checking online status**: fresh `intercom status/list` serves only to verify the full current contact ID and online status of the owner already selected by responsibility. Do not enumerate online/same-cwd sessions to discover recipients, infer identity from matching names/aliases, or message guessed recipients. Distinguish "unregistered", "registered but current contact unverified", and "ended"; registration time is not a heartbeat. Looking up the registry does not itself authorize arbitrary contact or remote writes.
- **Resolve unclear ownership upward first**: for unregistered or ambiguous ownership, ask the known immediate superior specifically to help locate the owner, escalating level by level to the top-level owner/user if necessary. Do not invent relationships, infer owners from cwd, or probe unrelated peers. If an identified predecessor's contact is missing/currently unreachable, use the next section's bounded consultation process under existing user authorization, limited to questions about the current responsibility. Pause only the affected matter; independent work continues.
- **Do not widen notifications**: do not broadcast "Who knows?", FYIs, general capability/skill announcements, or unverified guesses to everyone. Broadcast only when the user explicitly requests notification to the whole audience, within their specified audience/topic. "Important", "global change", "new skill", or a shared repository alone grants no authorization. Target necessary cross-scope collaboration by actually affected responsibilities; ask the user to confirm the audience scope before broader notification.
- **Minimize information**: messages contain only the question/purpose, relevant project/task identifiers, and the minimum evidence the recipient needs to act; distinguish observations, hypotheses, and unverified content explicitly. Do not forward unrelated logs/whole conversations or inject unrelated speculation into another owner's context/memory.

The successor first verifies and registers their owner identity (initially without a task if needed); the original owner or authorized immediate superior proactively performs atomic `handover`. Explicitly specify unfinished goals/acceptance criteria/dependencies, the successor's superior, active child run IDs/custodians/reporting paths (verify and explicitly state none if absent), existing write coordination, and the renegotiation plan. If superiors differ, provide explicit authority evidence for the reporting-relationship change; do not silently change parent for all of the successor's responsibilities. Old write agreements are released; old confirmations do not transfer to the new owner. The new responsibility retains inherited obligations and must obtain fresh confirmations before overlapping mutation. Registration does not automatically change the supervisor of running children; keep them under the original owner's custody with results passed to the successor as agreed, or hand them over/stop them through actual governance.

Report old/new responsibility IDs, who→whom, inherited responsibilities, and arrangements; **after A→B→C, A/B and both handovers remain queryable long-term**. Record the actual time for live handovers. To backfill a known past event, use explicit timezone-aware second-resolution `--occurred-at`; if the past seconds are unknown, mark `unknown` / `approximate` and record registration time separately, never pass off the current time as the past. Identical repeated requests are idempotent and create no fictitious handover. Do not confuse an Intercom session handover with a responsibility handover. Keep the original responsibility and escalate through the hierarchy if the successor is not secured; do not silently release it.

## Consultation After a Predecessor's Session Closes

A current owner may independently consult a predecessor about responsibility questions; a closed session is not a reason to push the question back to the user. Locate the predecessor through that handover's `predecessor_context` snapshot first, then use fresh `intercom status/list` to verify the **full original contact ID**. If the alias/identity is uncertain, first ask the recipient to confirm their actual Pi session ID; only a match establishes the old session as online and permits the bounded question. Do not pick the first same-cwd session, broadcast, or investigate unrelated sessions.

When offline, delegate bounded preparation/consultation as described in [references/predecessor.md](references/predecessor.md): `predecessor.py prepare` verifies the exact file header ID/cwd, copies only that old transcript, and generates a read-only, no-tool plan using `pi --fork <copy> --session-dir <new-directory> --print` from the original cwd; **prepare does not start Pi**. This explicitly user-authorized consultation is not a CLI fallback after subagent infrastructure failure. When a leaf is forbidden to start another agent, the owning parent personally schedules this restricted advisory CLI, while preparation/interpretation still goes to a governed async subagent. Do not let a leaf secretly start an unrestricted agent or fan out recursively. Use tmux + completion notification for long tasks; do not block waiting for subagents.

Label replies from the online old session, advice from forked old context, and reconstruction from materials separately; the latter two are not replies from the original live session itself and restore no ownership/repository write permissions. Record the question, predecessor/source, answer/evidence, uncertainties, and timezone-aware second-resolution time. If the file/cwd/actual ID is missing or the restricted CLI lacks the selected provider, report the precise blocker and escalate through the immediate superior; continue independent work, never guess the latest session or silently switch models/execution modes. Consultation is lateral knowledge retrieval; decisions/progress still follow the superior/subordinate hierarchy.
